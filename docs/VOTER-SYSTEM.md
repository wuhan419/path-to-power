# 选民系统设计（VOTER-SYSTEM）

> 面向接手者。读完这一份，你应该能说清：**选民为什么会变、变了又会影响什么、参数在哪、怎么验证没改坏平衡。**
> 配套：字段契约见 [`CONTENT-SCHEMA.md`](./CONTENT-SCHEMA.md)；开发流程见 [`DEVELOPMENT-GUIDE.md`](./DEVELOPMENT-GUIDE.md)。

---

## 0. 一句话结论

选民池是一局游戏里**唯一会自己呼吸**的资源：它在平静的月份里缓慢攒起来，
在事件的成败里剧烈起落，最后折算成**你还能不能往上走**的胜算修正。

它的存在意义不是"再加一根进度条"，而是回答一个问题：
**你手上那点民意，够不够支撑下一步？**

## 1. 为什么要重做（背景）

v0.5.2 只做了一半：

| 做完了 | 没做 |
|---|---|
| `G.voters = { warm, diehard, oppose }` 的数据结构（绝对人数，不是百分比） | **自然增减**：平静月完全不碰选民 |
| `applyVoters` / `electorateSize` / `rescaleVoters` / `electionStrength` | **事件系统性增减**：全项目只有 9 个内容文件手写了 `effects.voters`，其余 100+ 事件对选民零影响 |
| 升位稀释（`carryKeep`）+ 当选自带基本盘（`winShare`） | **影响面**：只有"晋升进度"的 20% 权重用到了选民，政策推进 / 连任完全没接 |
| 职位卡上的三档人数显示 | **观感**：T0 开局是 `0 / 0 / 0`，玩家看半天不动，判定为"没实装" |

用户实测原话：**「这套选民系统好像还没有实装」** —— 判定准确：它当时是**静态数据**，不是系统。

## 2. 数据模型（未改动）

```
G.voters = { warm, diehard, oppose }     // 单位：人（绝对人数，不是百分比）
```

选它的理由（v0.5.2 的设计决定，保留）：基层好感不该是 `-100~100` 的抽象条 ——
"满了"是什么意思？全国都满意吗？**人数是可数、可解释、会因选区扩大而被稀释的。**

三档语义：

| 档位 | 含义 | 在判定里的角色 |
|---|---|---|
| `diehard` 死忠 | 几乎必到票 | **最硬**：`×3` 权重。只有打赢事件 / 当选才涨，自然增长极慢 |
| `warm` 有好感 | 看你表现的可能票 | 主力票仓，`×1` 权重。自然增长的主战场 |
| `oppose` 反对 | 对手的票 | 帮对手 `×2` 权重。**在任就必然增长**（你做了决定就有人不满） |

选区规模随层级放大（`balance.voterBase.electorate`）：

| 层级 | T0 | T1 | T2 | T3 | T4 | T5 |
|---|---|---|---|---|---|---|
| 注册选民 | 5 千 | 6 万 | 30 万 | 75 万 | 900 万 | 2.4 亿 |

所有规则都按**选区规模的比例**算，不写死人数 —— 否则 5 千人的选区会瞬间爆表，而 2.4 亿的选区毫无感觉。

**选举底气**（界面读数，`electionStrength()`）：

```
mine   = diehard × 3 + warm
theirs = oppose × 2
rest   = max(0, size − diehard − warm − oppose)
pct    = mine / (mine + theirs + rest × 0.35) × 100      // 未定盘按 35% 折算
```

## 3. 触发①：自然增减（日常工作）

**每个平静月结算一次**（由 `engine/time.js → advanceMonth → vignette.js → settleQuietMonth` 驱动）。

用的是**均值回归**，不是固定累加：

```
目标 = 选区规模 × 目标份额
     warm    : 8%      ← 与"当选份额 winShare"同一语义：正常在任者应有的基本盘
     diehard : 2%      ← 自然只出"有好感"，死忠必须靠事件打赢
     oppose  : 4%      ← 你做了决定，就必然积累对手

每个平静月：delta = (目标 − 当前) × monthly × 轨道系数 × 声望系数
                     monthly = 0.05（每月收敛 5% 差额）
                     轨道系数：选举 1.5 / 名人 1.3 / 委任 0.9 / 操盘 0.8 / 财富 0.7
                     声望系数 = 0.6 + 声望/100
```

为什么用均值回归而不是"每月 +N"：

1. **天然有上限** —— 挂机 40 年也不会把池子挂满，不需要额外的封顶逻辑；
2. **事件赢来的超额支持会缓慢回落** —— 注意力是要不断续费的；
   赢了 2 万人，几个月不做声，他们会重新变回"未定盘"；
3. **升位自动适配** —— 换选区后目标跟着规模变，不需要特殊处理。

量级感受（T1，选区 6 万，声望 30，选举轨道）：

| 月份 | warm | diehard | oppose |
|---|---|---|---|
| 第 1 月 | +324 | +81 | +162 |
| 约 5 年后 | ≈ 4800（目标） | ≈ 1200 | ≈ 2400 |

## 4. 触发②：事件成败（有分量的事）

所有事件结算时自动附带，**不需要内容逐条声明**：

```
base   = 选区规模 × eventBase[量级]         // major 0.6% / mid 0.25% / minor 0.08%
delta  = base × byOutcome[判定档位] × categoryMul[事件类型]
```

档位表（负数=流失/反噬）：

| 档位 | warm | diehard | oppose |
|---|---|---|---|
| crit 大成功 | **+2.00** | +0.45 | +0.45 |
| ok 成功 | +1.00 | +0.18 | +0.22 |
| meh 勉强 | +0.30 | +0.05 | +0.15 |
| fail 失败 | **−0.35** | −0.10 | +0.55 |
| critfail 大失败 | **−0.80** | −0.25 | **+1.00** |

> 不对称是刻意的：**骂声比掌声传得远**。失败时反对者涨 0.55，远大于好感掉的 0.35。

事件类型系数（`categoryMul`）—— 家里的、恋爱的选民看不见：

| 类型 | 系数 | 类型 | 系数 |
|---|---|---|---|
| media 媒体 | 1.3 | career 仕途 | 0.7 |
| political 政治 | 1.2 | demo 族群 | 0.6 |
| scandal 丑闻 | 1.1 | shady 灰产 | 0.6 |
| civil 民权 / crisis 危机 | 1.0 | finance 金钱 | 0.5 |
| foreign 外交 | 0.8 | romance 感情 | **0.15** |

**三条让位规则**（内容作者优先级最高）：

1. 内容显式写了 `effects.voters` → **完全以内容为准**，不自动附加；
2. 事件本身改变身位（`effects.tier` / `fall` / `hardEnd`）→ 不自动附加
   （当选自带的基本盘由 `effects.tier` 那套单独发，避免同一件事算两次）；
3. 恋爱/家庭类事件系数极低，接近无影响。

合并用 `withEventVoters()`：它返回**新的** effects 对象（不改内容包原件），
并且**结算与显示共用这一个对象** —— 保证"账面上写的"和"实际扣的"永远一致。

## 5. 触发③：反噬 —— 选民影响什么

核心是一个有界的修正值：

```
voterEdge() = clamp( (选举底气% − edgeCenter) / edgeSpan , −1, +1 )
            edgeCenter = 27（自然均衡点）    edgeSpan = 35
```

**为什么中心点是 27% 而不是 50%：** 因为按自然 drift 收敛出来的均衡态
（warm 8% / diehard 2% / oppose 4%）算下来 `pct` 正好是 **27%**。
把中心放在那里意味着：**正常经营的玩家修正为 0**，既不奖励也不惩罚 ——
所以这个系统不会推翻既有的 300 局平衡（这一点已被校验器锁住，见 §7）。

修正值 `× contestW(0.08)` 就是 **±8% 胜算**。它接进三个地方：

### 5.1 晋升 / 连任（已实装，自动生效）

`computeP()` 检测到选项是**交给选民裁决**的（任一档位含 `tier + 1`，`isContestChoice()`），
就自动附加 `{ src: "voters", w: contestW }`。

**内容不需要改一行** —— 已有的 8 个 `prog_*` 晋升事件自动吃到了这个修正。
判定明细里会显示成 `选民底气 27%` 这一项，玩家点开"判定明细"能看到。

效果：票仓扎实的人晋升胜算 `0.573`，空票仓的人 `0.431`（同 base 0.5）。

### 5.2 政策推进（已提供机制，等内容接入）

政策推进类选项由内容**显式声明**：

```js
mods: [{ src: "voters", w: 0.12 }]      // 选民底气在这个选项上占 ±12%
```

`evalMod()` 已实现 `src: "voters"`，取 `voterEdge() × w`。

> ⚠️ **注意**：引擎侧只提供了"修正"这一根钩子，**"政策推进"这个玩法本身目前不存在**
> （全项目搜不到 policy / bill 相关机制）。所以这一条是**接口就绪、玩法待定义**，
> 见 §8 待确认项。

### 5.3 晋升进度（v0.5.2 起已有，保留）

`promotionProgress()` 里选民占 20% 权重：`voterScore = min(1, 底气% / 45)`。
加上 `× 0.20` 后进进度条，到 60 进入"机会区间"。

### 5.4 界面上看得见的地方

- **顶部状态条 · 职位卡**：`选民：死忠 N · 有好感 N · 反对 N（选举底气 X/100）`
- **月卡成长行**：平静月会报 `好感选民 +917`（有变化才写，没变化不占版面）
- **事件收益框**：自动增减与显式 `voters` 一样显示成 `好感选民 +864`
- **判定明细**：晋升类选项会多出 `选民底气 27%` 一行

## 6. 参数总表

全部集中在 `content/01-config.js` 的 `balance.voterDynamic`（**改这里不用动引擎**）：

| 键 | 默认 | 含义 |
|---|---|---|
| `enabled` | `true` | 总开关（关掉=退回 v0.5.2 的静态行为） |
| `monthly` | `0.05` | 每月收敛 5% 差额 → 从 0 到目标约 5 年 |
| `targetShare` | `0.08` | 目标「有好感」占选区规模比例 |
| `diehardTargetShare` | `0.02` | 目标「死忠」 |
| `opposeTargetShare` | `0.04` | 目标「反对」 |
| `repWeight` | `0.6` | 声望系数基准（`0.6 + 声望/100`） |
| `track` | 见配置 | 各轨道的自然增长系数 |
| `eventBase` | `{major:0.006, mid:0.0025, minor:0.0008}` | 事件基础量（占选区规模比例） |
| `byOutcome` | 见配置 | 五档判定 → 三档选民增减 |
| `categoryMul` | 见配置 | 事件类型 → 可见度系数 |
| `contestW` | `0.08` | 晋升/连任类选项的自动修正权重（±8%） |
| `edgeCenter` | `27` | 修正为 0 的底气百分比（对齐自然均衡点） |
| `edgeSpan` | `35` | 每偏离多少个百分点记 ±1 |

相关但不在本块的配置：`balance.voterBase`（`electorate` 规模表 / `carryKeep` 升位带走比例 / `winShare` 当选份额）。

## 7. 怎么验证没改坏

```bash
cd dev
# 300 局生涯回归 + 全量契约校验（约 5 分钟）
NODE_PATH=/Users/dfiuser/.workbuddy/binaries/node/workspace/node_modules \
  /Users/dfiuser/.workbuddy/binaries/node/versions/22.22.2-3/bin/node tools/validate.js
# UI 冒烟（约 1 分钟）
NODE_PATH=/Users/dfiuser/.workbuddy/binaries/node/workspace/node_modules \
  /Users/dfiuser/.workbuddy/binaries/node/versions/22.22.2-3/bin/node tools/smoke-ui.js
```

`validate.js` 里已锁住的**选民动态断言**（改这块就会被这些断言接住）：

- 目标基本盘 = 规模 × 8%/2%/4%
- 首个平静月好感与反对**同时净增**
- 连跑 400 个月后**收敛到目标附近**且**三档之和不超选区规模**
- 高于目标时 drift 为**负**（超额支持会回落）
- 大成功/失败/大失败的增减方向与相对大小（大失败反对者涨得最多）
- 显式 `voters` **优先**、升位类事件**不重复计**
- 恋爱类影响**远小于**政治类
- **自然均衡态（27%）处 voterEdge 正好为 0** ← 这条是"不推翻平衡"的保险丝
- 票仓扎实时晋升胜算更高 + 判定明细含「选民底气」
- 月卡成长行会报出选民变化

**看 300 局分布时重点盯**：`层级分布`（别让晋变难/变易太多）与 `结局分布`
（尤其 `retire_low` 与 `death_health` 有没有被推歪）。改了 `monthly` / `byOutcome` 之后必跑。

### 7.1 平衡影响：做过 A/B（结论：在噪声范围内，不用重新平衡）

做法：把 `voterDynamic.enabled` 改 false 跑一遍 300 局，再开 true 跑一遍，对比分布。

| 指标 | 关掉选民动态 | 开启选民动态 |
|---|---|---|
| T0 / T1 / T2 / T3 / T4 / T5 | 104 / 41 / 39 / 40 / 43 / 33 | 97 / 32 / 56 / 33 / 44 / 38 |
| retire_low | 99 | 93 |
| death_health | 82 | 88 |
| retire_high | 40 | 39 |
| retire_kingmaker | 40 | 35 |
| retire_fallen | 20 | 27 |

差异都在 n=300 的抽样噪声内（最大的一格 T1/T2 也只到 ~1.8σ）。
**设计上也就该如此**：`edgeCenter` 对齐自然均衡点，正常玩家的修正恒为 0。

> 对照参考：真正推歪分布的是**内容批次**（128 → 156 事件），不是这次改动 ——
> 加事件前 T0 是 147、T5 是 25；加完事件无论选民动态开关，T0 都掉到 ~100。
> 所以发现 T0 变少时，先去看内容批次，别急着怀疑选民。

## 8. 隐含假设与待确认项

> 这一节是**故意留在文档里的开放式问题**。下面每一条都是当前实现的隐含前提，
> 如果和你的设计意图不符，改起来都是一处参数或一小段代码。

### 已按下面这些假设实现（如不认同请指出）

1. **自然增长只有正向的门槛，没有"不做事的惩罚"** ——
   实现成"向目标收敛"而不是"低于目标还要往下掉"。所以完全不经营也能到 27%。
   若要体现"疏于经营会掉"，需要再加一层衰减。
2. **死忠（diehard）自然只长到规模的 2%** —— 死忠必须靠事件/当选获得。
   理由是"死忠"这个词有分量，不该靠时间攒出来。
3. **反对者也自然增长** —— 在任就是会有人不满，哪怕你什么都没做错。
   这是把"在位即代价"做实的一种方式。
4. **`edgeSpan = 35`、`contestW = 0.08`（±8%）是手感估计值，没有真实调参依据** ——
   只做过"中心归零、有界、单调"的验证。是否太强/太弱需要你实际玩几局判断。
5. **事件自动增减只在"没有显式 voters、且不改变身位"时生效** ——
   内容作者写了就以内容为准。目前 9 个文件写了 `voters`，
   其余事件现在会开始自动影响选民。
6. **"选举连任"目前没有独立玩法**，只体现在"晋升类选项吃选民修正"上。
   真正意义上的**任期制/改选周期**（到点必须打一场连任战，输了就下野）**没有实现** ——
   `tierGates` 只是"晋升前最少熬够多少个月"的下限，不是任期上限。
7. **"政策推进"玩法不存在**，只提供了 `src: "voters"` 这个修正钩子。

### 需要你定的事（按影响面排序）

| # | 问题 | 备选做法 | 影响 |
|---|---|---|---|
| A | 要不要做**任期制**（到点改选，选民底气决定连任成败）？ | ①不做（当前）②只对部分层级做（如 T1/T2 市州议员）③全层级做 | 做的话会显著改变 300 局分布，需要重新平衡，且要新增一类"到点触发"的事件钩子 |
| B | 要不要做**政策推进**玩法？ | ①不做 ②做成"攒够选民底气+派系支持才能推法案，推成加声望/加选民" | 目前只有修正钩子，没有任何载体（没有法案数据表、没有政策池） |
| C | 自然增长的**强度**（`monthly` 0.05）合适吗？ | 调大=选民变化更快更"活"，调小=更慢更"稳" | 直接决定玩家多久能感知到选民在动 |
| D | 失败时**反对者涨得比好感掉得快**（0.55 vs 0.35）够不够狠？ | 加大差距=失败代价更痛 | 影响"敢不敢做大事"的手感 |
| E | 是否要**选民影响事件池**（票仓结构决定你能抽到什么）？ | 加一层权重（如深蓝区更容易出民权事件） | 未实现；属于"选民影响面"的第四条，与现有事件加权管线可复用 |
