# 投注经济设计（STAKE-ECONOMY）

> 面向接手者。读完这一份，你应该能说清四件事：**判定前"加码"的钱价是怎么算出来的、
> 为什么它不能是常数、参数在哪、怎么验证没改坏 300 局平衡。**
> 配套：字段契约见 [`CONTENT-SCHEMA.md`](./CONTENT-SCHEMA.md) §4.4；开发流程见 [`DEVELOPMENT-GUIDE.md`](./DEVELOPMENT-GUIDE.md)；项目总览见 [`README.md`](../README.md)。

---

## 1. 这套机制是什么

判定前玩家可以"投入资源加码"（D&D 式的加码下注）：**资金 / 精力** 抬判定目标值，
**人情** 换一次重投取优。加码只提高这一判定的胜算，**不增加事件本身的回报**。

资金这一项有一个汇率问题：**一档多少钱、一档买多少胜算**。本文只讨论**「一档多少钱」**
（`per`）。「一档买多少胜算」（`w: 4%` / `cap: 30%`）没有改，理由见 §6。

---

## 2. 现状：v0.7 之前是常数，两个后果

v0.5–v0.6 的配置是一行常数：

```js
stakeRates: { fun: { per: 250000, w: 0.04, cap: 0.30 } }   // 每档固定 $250k → +4%，上限 +30%
```

用户在实测里指出这不对（原文）：

> 「这个不应该是固定的吧。应该根据现在的职位和现在的事件动态的汇率。和金额……
> 我是一个社区 NGO 小兵和我是州长，促成一件事花费的代价能一样吗？对吧。
> 并且针对不同收益事件也应该动态调整。比如我收益只有 50k，你让我花 250k 去提升概率？」

对照真实数据，两个后果都能验证：

**后果 ①：低身位的资金投注栏是死的。** T0 选举轨月薪 $1,000（`reg.officeSalary`），
月度结余大致持平，开局家底 `startFun: 10000`。而一档 $250k ——
`floor(10000 / 250000) = 0`，**永远投不进第一档**。查一下全库 45 个带 `stake.fun` 的选项就能看到：
这个功能实际只对 T3 以上、且攒过钱的玩家存在。

**后果 ②：价码与事情的钱量级脱钩。** 全库带 `stake.fun` 的选项，其自身"钱量级"分布是
（`stakePot` 口径，见 §3.2）：

| 分位 | 10% | 25% | 50% | 75% | 90% |
|---|---|---|---|---|---|
| 钱量级 | $18k | $60k | $150k | $260k | $800k |

最小值 $14k（1960 年买电台时段），最大值 $2.6M。**固定 $250k/档**意味着：
在 $14k 的事情上，你被要求花 $250k 买一档 +4%（约为事情本身的 18 倍）；
而在 $800k 的事情上，同样的 $250k 是合理的。同一个数字不可能同时对。

## 3. v0.7：每档价码由两个锚算出来

```
per = min( √(A × X) , X )        ，再夹进 [perMin, perMax] 并抹成整数
```

### 3.1 身位锚 A —— 你这个位子办一件事的常规手笔

```
A = 职位月薪(track, tier) × perSalaryMonths × gradeMul
```

- **职位月薪取 `P.officeSalary()`**，来源是 `reg.officeSalary["track_tier"]`
  → miss 退 `"*_tier"` → 再退公式 `salaryBase × (1 + tier × salaryPerTier)`。
  **这与平静月的工资是同一个函数**（`P.quietAccount()` 也调它）。
  项目已有的原则是「身份直接决定日常收益 —— 市议员和联邦参议员的工资差一个数量级」，
  投注价码应该服从同一个口径。改工资表 = 同时改了收入与下注价码，这**是有意的**。
- `perSalaryMonths: 3` —— 一档 ≈ 你三个月的薪水。
- `gradeMul` —— 事件没写钱时，按量级缩放：`minor 0.6 / mid 1.0 / major 1.8`
  （全库 `grade` 只有这三个值：minor 32 / mid 79 / major 53）。

各身位的锚（`perSalaryMonths = 3`）：

| tier | 选举轨月薪 | A(mid) | 财富轨月薪 | A(mid) |
|---|---|---|---|---|
| T0 | $1.0k | $3.0k | $2.0k | $6.0k |
| T1 | $2.5k | $7.5k | $5.0k | $15k |
| T2 | $6.0k | $18k | $12k | $36k |
| T3 | $8.0k | $24k | $25k | $75k |
| T4 | $16k | $48k | $50k | $150k |
| T5 | $33k | $99k | $100k | $300k |

### 3.2 事件锚 X —— 这件事本身值多少钱

```
pot = max( |cost.fun| , 各档 |effects.fun| , |cost.fun × funMul| )
X   = pot × potShare          （potShare = 0.25）
```

- `cost.fun` —— 明码标价的代价（"花 $400k 请律师团"）
- `effects.fun` —— 直接给/扣的钱（"这一笔赚 $150k"）
- `funMul` —— 按本金的百分比（"押多少赚 200%"），本金就是 `cost.fun`，折算回美元
- 一个钱都没写的选项 `pot = 0`，此时**只用身位锚**（`per = A`）

### 3.3 合成：几何平均 + 事件锚封顶

取几何平均而不是算术平均，是为了让**两支都不会被另一支拖到极端**：

- `A < X`（身位小、事情大）→ 走 √ 那支：`per = √(A·X)` 随身位抬升。
  小兵不能拿零头买下大事（`per` 被身位抬起来）。
- `A > X`（身位大、事情小）→ 被 `X` 夹住：`per = X`。价码跟着事情走，
  大佬也不为小事掏大钱。

**不变量（可断言、已断言）**：

```
8 档总投入 = 8 × per ≤ 8 × X = 8 × pot × 0.25 = 2 × pot
```

即**投满也只能押到事情本身钱量级的 2 倍**。这条直接消灭了后果 ②：
"花 $250k 去搏 $50k" 在数值上不可能再出现。

### 3.4 三条让位规则

1. **内容写死 `per` 时以内容为准**（`stake: { fun: { per: 777000 } }`），
   该选项完全关闭动态换算，`__rate.source` 标为 `"content"`。
   —— 剧情需要"这一注就是天价"时用得上。
2. **`pot` 极小时**（< `perMin`）价码退到 `perMin` 兜底。全库最小的 `pot` 是 $14k
   （`X` = $3.5k > `perMin` = $500），所以这条只是安全网，实际不会触发。
3. **`stake` 里没声明 `fun` 的选项**不参与（只投精力/人情），与本文无关。

## 4. 实际算出来的价码

同一个选项（`cost.fun = $400k`，pot = $400k，grade = mid）在各身位的每档价码：

| tier | T0 | T1 | T2 | T3 | T4 | T5 |
|---|---|---|---|---|---|---|
| 每档 | $17k | $27k | $42k | $48k | $69k | $99k |

换成"这件事值多少钱"的视角（T3 选举轨，`X` 随 `pot` 走）：

| 事件钱量级 | $50k | $400k | $2M |
|---|---|---|---|
| 每档 | $12k | $48k | $105k |
| 投满 8 档 | $96k（1.92× pot） | $384k…（被 X 夹住：2.00×） | $840k（1.54× pot） |

两条曲线都在动 —— 这就是用户要的"汇率随职位与事件金额动态调整"。

**用户报的核心 bug 已修**：T0 选举轨、家底 $10k（开局数值）
→ 对 $50k 钱量级的事件可投 **1 档**，对没写钱的事件可投 **3 档**。
v0.6 的固定汇率下这两个数都是 **0**。

## 5. 界面上怎么交代这件事

动态汇率如果不解释，就成了新的黑箱 —— "上次同样的选项是 $250k，这次怎么 $6k"。
所以投注面板在投入行下方多一条 `.stake-rate`（`P.stakeRateNote()`），把依据摊开：

```
每档 $17k：身位基准 $3k（月薪 $1k × 3 个月），事情价码 $100k（事件钱量级 $400k 的 25%）
 —— 取两者之间：位子越高越贵，但不会超过这件事本身值多少。
```

三种来源各有一套措辞（身位+事件 / 只按身位 / 剧情写定），见 `P.stakeRateNote()`。

金额一律走 `P.fmtUsd()`：`$400` / `$6.1k` / `$1.5M`。
面板上原来是写死的 `$xxxk` 拼接，在动态汇率下会显示成 `$17k` 对不上 `$17321`，所以统一了口径。

## 6. 没改什么，以及为什么

- **`w`（每档 +4%）与 `cap`（+30%）没改。** 加码的"杠杆"和"天花板"是判定平衡的一部分，
  而本次要修的是"价码与事情的钱量级脱钩"。改了 lever 会让 300 局的胜率整体漂移，
  与本次诉求无关。**如果以后要动 `cap`，等于是重新平衡，必须单独跑 A/B 并写清楚。**
- **精力与人情的汇率没改。** 精力是"你自己的体力"，不随身位换算（一个州长的一点精力
  不比一个实习生的更"贵"，但它也不更便宜）；人情是开关式（1 点换一次重投）。
  这两项没有"金额"可锚，所以保持常数。**这是 §9 的一条隐含假设。**
- **判定数学没改。** `computeP` / `rollTier` / `clamp(0.05, 0.95)` 一行没动。

## 7. 参数总表

全部在 `content/01-config.js` 的 `balance.stakeRates.fun`：

| 参数 | 默认 | 含义 | 调它的后果 |
|---|---|---|---|
| `w` | `0.04` | 每档加多少胜算 | 加码的杠杆；动它要重跑 A/B |
| `cap` | `0.30` | 该项加成的总上限 | 同上；`cap ÷ w` 决定可投档数（= 8） |
| `perSalaryMonths` | `3` | 身位锚 = 月薪 × N | 调大 → 全程更贵；调小 → 小兵更容易投满 |
| `gradeMul` | `{minor:0.6, mid:1.0, major:1.8}` | 事件没写钱时的量级系数 | 只在 `pot = 0` 的选项上生效 |
| `potShare` | `0.25` | 事件锚 = pot × N，同时是总投入硬顶的 1/2 | 调大 → 大事更贵、小事的天花板更高 |
| `perMin` / `perMax` | `500` / `5000000` | 价码兜底夹取 | 安全网 |

## 8. 怎么验证

```bash
node tools/validate.js                          # 300 局，种子 20260921
node tools/validate.js --games=300 --seed=7     # 换种子复算
node tools/smoke-ui.js                          # 界面断言（含汇率说明条）
```

### 8.1 模拟现在是**可复现**的

引擎一律用 `Math.random()`，那让"跑两次"必然有随机差异 —— n=300 时某个结局 ±10 局
完全可能是噪声，A/B 就没法定论。所以 `validate.js` 在**模拟阶段**把 `Math.random`
换成定种 PRNG（mulberry32），前后恢复。A/B 于是能在**同一批生涯**上比较。

> ⚠️ 长跑注意：本机把 `--games` 拉到 900 会被资源上限杀掉（SIGKILL）。
> 需要更大样本时，**换多个种子各跑 300 局再汇总**，不要单体拉大。

### 8.2 投注观测行（每次跑都会打印）

```
投注观测：押过钱的判定 7.1% 次（平均 1.51 档）｜ 每局押掉 $1098k
```

这一行是给 A/B 用的：**分布一变，先看这一行** ——
否则分不清是机制变了、还是模拟里投注的频次/金额变了（下面 §8.3 就踩过这个坑）。

### 8.3 A/B 方法（照抄就能复现）

把动态汇率钉死回 v0.6 的常数，其余一行不动，然后同种子跑两臂：

```bash
cp -R dev /tmp/dev_fixedstake
# 在副本的 engine/dice.js 里给 P.stakeFunPer 开头插一行：
#   return { per: 250000, pot: 0, anchor: 250000, ceiling: null, source: "office", raw: 250000 };
```

### 8.4 实测结果（种子 20260921，300 局）

| 观测 | 固定 $250k | 动态汇率 | 差 |
|---|---|---|---|
| 层级 T0 / T1 / T2 / T3 / T4 / T5 | 101 / 42 / 47 / 33 / 40 / 37 | 99 / 48 / 36 / 43 / 35 / 39 | ≤ ±11 |
| `death_health` | 94 | 91 | −3 |
| `retire_low` | 93 | 96 | +3 |
| `retire_high` | 30 | 34 | +4 |
| `retire_fallen` | 26 | 15 | −11 |
| `retire_kingmaker` | 38 | 37 | −1 |
| `retire_comeback` | 16 | 14 | −2 |
| `retire_media` | 3 | 13 | +10 |
| 押钱的判定占比 | 2.8% | **7.1%** | +2.5× |
| 每局押掉的钱 | **$4,535k** | **$1,098k** | −76% |

读法（重要，别只看分布那一列）：

- **最大的变化不在分布，在"谁能参与"。** 押钱的判定从 2.8% → 7.1%，
  但**每局押掉的钱反而少了 76%**（$4.5M → $1.1M）。也就是说：同一个资金黑洞，
  现在由更多人分摊、每人每次小得多 —— 这正是设计意图（"小兵也该投得起一档"），
  而且它**没有**让经济总量失衡。
- **分布的变化都在 ±4pp 以内**（n=300、配对）。两个最大的位移
  （`retire_fallen` −11、`retire_media` +10）方向一致且可解释：押注金额变小 → 手里留下的钱更多 →
  更能付得起"好选项"的代价 → 更少跌落。**不构成需要重新平衡的理由。**
- 如果要更紧的置信区间，按 §8.1 换 3 个种子各跑 300 局汇总（900 样本/臂）。

## 9. 隐含假设（需要用户确认）

按本项目的规矩，把这次实现里**替你做主的地方**逐条列出来：

1. **身位锚用"职位月薪"而不是"现有家底"。** 用月薪（职级）代表身位，
   所以**同层级下不同的钱不一样**（财富轨 T5 月薪 $100k → 价码比选举轨 T5 的 $33k 贵 3 倍）。
   如果希望"价码只看你现在有多少钱"，这是另一套设计（会变成"穷人恒便宜"）。
2. **`perSalaryMonths = 3`** —— 一档 ≈ 三个月薪水。这个倍数是拍的，
   它决定"一档有多痛"。想更痛就调大。
3. **`potShare = 0.25`** —— 投满 ≈ 事情本身钱量级的两倍。这个"赌注上限"是拍的。
4. **`gradeMul` 只在事件没写钱时生效。** 有 15/45 个 `stake.fun` 选项 `pot = 0`，
   它们完全靠 `gradeMul` 区分大小事。如果认为 `grade` 不该影响钱价，把它全设成 1。
5. **精力/人情不随身位换算**（见 §6）。若认为"州长的一点精力"该更贵，需要另设一套锚。
6. **`w` 与 `cap` 未动**（见 §6）。所以本次改的是"价码"，不是"加码的性价比"。
7. **投注的经济意义仍是"纯胜算"**，不参与事件回报（`funMul` 的回报按**本金**
   计算，而本金 = `cost.fun` + 投注资金 —— 这条是既有行为，未改）。

### 待用户确认的开放问题

- **A. 要不要让 `cap` 也随事件浮动？** 现在大事小事都是"投满 +30%"，只是价码不同。
  另一种玩法是"大事能用钱撬动更多、小事撬不动"。
- **B. 财富轨道是不是该更贵？** 现在它按薪级贵 3 倍。也可以让它**更便宜**
  （"钱就是他的专业能力"）—— 那是完全不同的人物手感。
- **C. 要不要给"钱不够但有前途"的玩家一条路**（比如贷款 / 政治行动委员会），
  让低身位的资金投注不只停在 1 档？

## 10. 代码地图

| 位置 | 干什么 |
|---|---|
| `content/01-config.js` → `balance.stakeRates.fun` | 全部参数与推导注释（§7） |
| `engine/core.js` → `P.officeSalary()` | 职位月薪的**唯一**口径；`quietAccount` 与投注共用 |
| `engine/dice.js` → `P.stakePot(choice)` | 算选项的钱量级（cost / effects.fun / funMul） |
| `engine/dice.js` → `P.stakeFunPer(choice, grade)` | §3 的公式本身；返回 `{per, pot, anchor, ceiling, source}` |
| `engine/dice.js` → `P.stakeSpec(choice, grade)` | 把动态 `per` 写回 `spec.fun.per`，下游无需知道它是算出来的 |
| `engine/dice.js` → `P.fmtUsd(n)` / `P.niceUsd(n)` | 金额显示 / 抹零（一律向下取整，宁可少收） |
| `engine/render.js` → `P.stakeRateNote()` | §5 的界面说明条 |
| `engine/render.js` → `P.renderStake()` | 投注面板（用动态 `per`） |
| `engine/style.css` → `.stake-rate` | 说明条的样式 |
| `tools/validate.js` → 「动态投注汇率」段 | ⑧ 组断言：身位轴 / 事件轴 / 硬顶 / 写死优先 / 抹零 / 文案 |
| `tools/validate.js` → 「投注观测」行 | §8.2 的 A/B 诊断 |

**下游不用改的味道**：`stakeSpec()` 把算出来的价码写回 `spec.fun.per`，
所以 `stakeMax` / `stakeInfo` / 面板渲染的逻辑一行没动 —— 它们只是拿到了不同的数字。
